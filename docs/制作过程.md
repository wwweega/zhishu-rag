# 知枢 · 制作过程：背景、选型与核心难点

> 这份文档记录"知枢"从 0 到 1 的完整建造过程：**为什么做、怎么选型、卡在哪、怎么解**。
> 它比 README 更"过程化"——README 讲"是什么"，这里讲"**当时是怎么想的、试错了什么、最后为什么这么定**"。

---

## 一、背景与目标

### 1.1 问题从哪来

企业内部的规章制度、采购流程、售后条款、产品手册，通常是这样散落的：

- PDF / Word / 扫描件混在一起，没有统一索引；
- 员工想查一条具体规定（"年假能不能顺延""5 万的设备谁审批"），要靠 Ctrl+F 逐份翻；
- 找 IT 搭个全文搜索，又只能关键词匹配，回答不了自然语言问题。

把文档直接喂给大模型看似能解决，但会立刻遇到两个硬伤：

1. **幻觉**：模型会一本正经地编造"公司规定年假可以顺延 6 个月"；
2. **不可溯源**：就算答对了，也说不出"这句话出自哪份文件的哪一条"，企业不敢用。

### 1.2 目标（可验收）

所以给自己定的目标是做出一个企业级 RAG 知识中枢，**核心验收标准是"可信"而非"能跑"**：

| 目标 | 可验收的表现 |
|---|---|
| 答得准 | 混合检索 + 重排后，制度类问题能答对 |
| 答得可溯源 | 每句结论带 `[证据N]`，且引用可**机器逐字校验** |
| 答不了就拒答 | 库外问题明确拒答，不编造 |
| 慢在哪说得清 | 端到端延迟能按阶段拆解，口径物理自洽 |
| 零门槛复现 | 没有 Milvus/PG/Redis/Key 也能跑通全链路 |

## 二、技术选型：每个选择都是一次取舍

### 2.1 整体链路为什么是"解析→分块→向量化→混合检索→重排→生成治理→引用溯源"

这是 RAG 的经典链路，但**每一环都有具体的"为什么不是别的"**：

**① 解析层：为什么要三级降级？**
企业内部文档的格式五花八门：电子版 PDF（有文本层）、扫描件（只有图像）、复杂版面（多栏/表格/公式）。
- 直接上 MinerU 效果最好，但它要下几个 GB 的模型，装机门槛高；
- 只用 PyMuPDF 轻量，但扫描件直接抓瞎。

**决策**：做**能力探测 + 逐级降级**——有 MinerU 就用 MinerU，没有就 PaddleOCR（扫描件），再没有就 PyMuPDF（文本层）。用户装什么就用什么，不强制。

**② 分块：为什么用"父子块 small-to-big"而不是固定长度切？**
- 固定长度切的致命问题：**要么太小丢上下文，要么太大召回不准**——鱼和熊掌。
- 父子块把两者拆开：**child（小块）负责"找到"，parent（大块）负责"看懂"**。检索用 child，命中后回溯 parent 喂给 LLM。

这是整个项目最核心的设计，后面踩的坑也大多围绕它。

**③ 检索：为什么是"向量 + BM25 混合"而不是只用向量？**
- 向量擅长语义（"顺延到什么时间" ↔ "跨年使用期限"），但**对精确串很弱**（"第三条""GB/T 1234""SN-2024-001"）；
- 企业文档里恰恰大量存在条款号、型号、编号。

**决策**：两路召回，缺一不可。

**④ 融合：为什么是 RRF 而不是加权求和？**
- 向量分和 BM25 分**量纲完全不同**（余弦 0~1 vs BM25 0~十几），加权求和要先归一化，而归一化方式又很敏感；
- RRF 只用**排名**，天然跨量纲：`score = Σ 1/(k + rank_i)`，k=60。零调参，换模型不用重调。

**⑤ 重排：为什么向量召回后还要 Cross-Encoder？**
一句话：**召回求全（recall），重排求准（precision）**。
向量是"粗筛"（双塔，query/doc 独立编码，快但粗），Cross-Encoder 是"精读"（query 和 doc 拼一起过模型，准但慢）。所以先用便宜的召回拿 top-20，再用贵的重排精挑 top-6。

**⑥ 生成治理：为什么要"强制 JSON + 句级引用 + 拒答"三道防线？**
把"引用"从**模型的礼貌承诺**变成**可机器验证的事实**。这是企业级和玩具的分水岭。

### 2.2 存储选型

| 组件 | 选择 | 理由 | 降级 |
|---|---|---|---|
| 向量库 | Milvus | 生产级、支持 HNSW 与标量过滤 | numpy 暴力检索 |
| 元数据 | PostgreSQL | 事务、JSON、成熟 | SQLite |
| 缓存 | Redis | 多副本共享、持久 | 进程内 LRU |
| 模型 | 百炼（OpenAI 兼容） | 国内可直连、qwen-plus 性价比好 | mock |

**共同原则**：每个外部依赖都必须有降级路径。"能降级"不是妥协，而是让**读者零门槛复现**——这是开源项目的生命线。

## 三、核心难点与解决方案（真实踩坑记录）

> 以下每一个都是开发过程中**真实遇到并修复**的。共同点是：**不报错，但结果变差**。
> 所以本项目的原则是"**跑通不算数，要跑对**"。

### 难点 1：`.md` 文档入库后静默产出 0 个块

**现象**：把 Markdown 语料入库，没报错，但知识库是空的。

**排查**：发现解析器无条件用 PyMuPDF，而它打不开 `.md`，失败后**静默返回空**。

**根因**：解析器没有按文件类型分发。

**解法**：`parse_document` **先按后缀分发**——`.md/.txt/.csv` 直接走文本解析器，`.pdf` 才进入"文本层探测链"。并补回归测试 `test_markdown_uses_text_parser`。

**启示**：**静默失败是最危险的失败**。宁可报错，不可装死。

---

### 难点 2：父子块关系建了但没用上（children=0）

**现象**：构建父子块后，日志显示 `children=0, parents=N`，检索质量莫名很差，但**没有任何报错**。

**根因**：`build_parent_child` 计算了 children 却**忘了 append 到结果列表**，父块被创建了，子块却丢了。

**解法**：补上显式 `children.append(c)`；补测试 `test_parent_child_relationship`。

**启示**：这类"数据静默丢失"是最难发现的——它不崩溃，只是悄悄让你的系统变笨。

---

### 难点 3：分块重叠窗口逻辑写反，整篇文档并成一个巨块

**现象**：分块后只有一个块，包含整篇文档。

**排查**：重叠逻辑 `buf = keep if keep_tok < buf_tokens else []` —— 条件恒真，导致 `buf` 永远被保留、永不切分，一篇文章越滚越大。

**解法**：改为无条件 `buf = keep`，并显式限制重叠上限。

**启示**：**边界条件写反不会报错，只会让结果"看起来还行但不对"**——必须用"块数是否合理"这类断言去卡。

---

### 难点 4：child 的 parent_id 指向失效的旧 id

**现象**：父块回溯拿不到内容，"small-to-big"名存实亡。

**根因**：`chunk_document` 里**先**用哈希给所有块分配了 id、回填了 child.parent_id，**后**才把父块的 id 改写成 `par_{doc}_{idx}`。于是 child 的 parent_id 指向了一个**早已不存在**的哈希 id。

**解法**：**先确定父块 id，再回填 child.parent_id**（保证引用的是最终 id）。

**启示**：**赋值顺序即正确性**。有相互引用的 id 时，必须"被引用方先定稿"。

---

### 难点 5：缓存版本号用时间戳 → 同一秒批量入库不失效

**现象**：批量入库两个文档，第二个入库后查询，仍命中第一个文档时期的旧缓存。

**根因**：缓存键里的知识库版本号用了 `int(time.time())`，同一秒内连续两次入库拿到**相同**版本号，缓存没被失效。

**解法**：改为**单调递增计数器**。

**进阶坑（同类问题，第二次踩）**：计数器放在**进程内全局变量**里 —— 多进程部署时各进程各一份；进程重启后归零，历史旧缓存**重新可见**（我在本项目里真实复现了"重启后又看到旧答案"）。

**最终解法**：版本号**存 Redis**（共享、持久），进程内只做后备。

**启示**：缓存的失效设计是分布式系统的经典难点，"看起来能失效"和"真的共享地失效"是两回事。

---

### 难点 6：引用 `verified=false` 假阴性 —— 证据原文两处登记

**现象**：模型明明引用了正确的句子，校验却判"未核对原文"。

**根因**：证据原文在**两个地方**分别登记（生成时一个、校验时另一个），两处遍历顺序/范围不一致时，校验用的原文和喂给模型的原文对不上。

**解法**：**"产生证据编号的地方，就必须是登记证据原文的地方"** —— 单一事实来源，把登记动作**内聚进** `build_evidence_block`。

**启示**：**单一事实来源（single source of truth）**是消除这类"两处不一致"的根本手段。

---

### 难点 7：模型把编号写在正文却不填 citations 数组

**现象**：答案正文里有 `[证据5][证据2]`，但结构化 `citations` 是空的。引用校验对空数组"0/0 通过"，看似没问题，实际上**"句级引用溯源"完全失效**——用户看到编号却点不开任何证据。

**解法**：**从 answer 正文正则提取 `[证据N]` 回填** `citations`，保证"正文标注"与"结构化引用"始终一致。

**启示**：**校验器"通过"不等于"有效"**。校验空集永远通过——这类"假阳性通过"比失败更隐蔽。

---

### 难点 8：阶段耗时超过端到端墙钟（阶段 10690ms vs 墙钟 5950ms）

**现象**：trace 里 retrieve 阶段耗时 10690ms，但端到端只有 5950ms —— **物理上不可能**。

**根因**：`stage_breakdown` 是"把同 kind 的 span 耗时求和"。但 retrieve 阶段内部**嵌套**了 query_rewrite / vector_recall / hyde / bm25_recall / rrf_fusion 五个子 span，**子 span 的耗时被重复计入**。

**解法**：每个阶段取**其所有 span 时间区间的并集**（重叠只算一次）。这与 `total_latency_ms` 同源同口径。补测试 `test_stage_breakdown_counts_nested_spans_once`。

**启示**：这个坑和我在"运营智脑"项目里踩的"墙钟 = max(span) 而非区间并集"是**同一类错误**——**时间统计必须用区间运算，不能用简单的加减**。

---

### 难点 9：假拒答 —— 拿 rerank 绝对分比固定阈值

**现象**：问"采购 5 万元设备谁审批"，语料里明明有这条规定，系统却**拒答**了。

**排查**：追踪发现——正确的块在融合阶段排第 1，但重排后 top 分只有 **0.19**，低于配置的固定阈值 **0.35**，于是被判"证据不足"。

**根因**：**拿 rerank 绝对分比固定阈值**。不同 reranker 的分数量纲完全不同（百炼 gte-rerank 对真正相关的块也只给 ~0.19，本地 bge 可能给 -10~10），固定阈值必然水土不服。

**解法**：改为**批内归一化 + 相对阈值**。同一个 query 的候选自成可比集合，`(score - min)/(max - min)` 归一化后量纲无关；只有当"整批归一化后 top 分仍很低"**且**"绝对分≈0"时才拒答。换 reranker 不用重调阈值。

**修复效果**：faithfulness 从 **0.8 → 1.0**（假拒答直接把正确答案吞了）。

**启示**：**"绝对分比固定阈值"是 RAG 里最典型的脆弱设计**。凡是分数，先问"这个分是什么量纲、和谁比"。

---

### 难点 10：`expand_parent` 用父块文本覆盖 child，导致引用张冠李戴

**现象**：问"迟到几次影响绩效"，答案是对的，但引用指向了一个**讲报销时限的块**。

**排查**：
1. 重排其实**正确**地把"第三条 每月迟到…"排在第 1（score 0.5）；
2. 但 `expand_parent` 把 child 的 text **替换成了父块全文**，父块恰好也包含这条规定，模型读父块答对了；
3. 可引用单元的 `chunk_id` 还是 child 的，但 `text` 已是父块 —— 于是模型按"第几条证据"数位置，乱标了编号。

**根因**：**混淆了"证据单元"和"上下文语境"**。small-to-big 的"big"应该是**补充语境**，而不该**覆盖**掉用于精确引用的 child。

**解法**：
- child 的 `text` **保留其原文**（用于逐字引用、高亮命中位置）；
- 父块放入**独立的 `parent_text`** 字段，作为"所在章节上下文（仅供理解，不要引用）"一并喂给模型；
- prompt 明确要求："引用前核对——我写的 quote 是不是就在这条 [证据N] 正文里逐字出现过？"

**修复效果**：引用从"✗未核对 / 张冠李戴"变成 **全部 `✓已核对原文` 且指向正确块**。

**启示**：**"小块做证据、大块做语境"**——这是 small-to-big 的正确姿势。把两者混在一个字段里，引用溯源必然崩。

---

### 难点 11：全局缓存无上限 → 内存泄漏

**现象**：`_QUOTE_CACHE` 是进程级全局字典，QPS 高时会随请求量**线性增长**，长跑必然 OOM。

**解法**：加 FIFO 上限（4096），超限淘汰最早一批。补测试 `test_evidence_text_cache_is_bounded`。

**启示**：任何"进程级全局状态"都要问一句：**它会无限增长吗？**

---

### 难点 12：测试互相污染 —— "单跑通过、全量跑失败"

**现象**：单独跑"空知识库拒答"测试通过，全量跑却失败。

**根因**：多个测试共用 `data/index/` 目录，前一个测试入库的数据让"空库"测试其实**不为空**。

**解法**：用 pytest `tmp_path` 给每个测试独立的向量库目录。**测试之间必须隔离**。

---

## 四、验证方式：怎么保证"真的对"

我给自己定的验证纪律是——**每改一处，必须用真实数据回归**：

1. **单测（34 个）**全部走降级后端，CI 里无需任何外部服务即可跑通；
2. **端到端 demo**：真实入 2 篇语料 → 问 5 个问题（含 1 个库外负例）→ 检查答案 + 引用 + 耗时口径；
3. **评测门禁**：10 题评测集（含 2 个拒答负例），CI 里按**单项下限**卡（不是平均值），拒答准确率必须 100%；
4. **可观测**：每条问答都有 trace，能下钻到 span 级看"慢在哪"。

**真实跑出来的结果**（非编造，详见 README 第五节）：

| 指标 | 数值 |
|---|---|
| faithfulness / relevancy / recall | 1.0 / 1.0 / 1.0 |
| llm_judge | 0.7 |
| 拒答准确率 | 2/2 |
| 平均延迟 / P95 | 6.9s / 9.1s |
| 单次成本 | ≈ $0.0009 |

## 五、局限与后续

**当前局限（诚实说明）**：
- 示例语料仅 2 篇、评测集仅 10 题，是**功能验证**而非统计基准；
- 未做鉴权/多租户/限流，聚焦 RAG 链路本身；
- 依赖 Key 的能力需自备，降级模式的效果**不可用于评估质量**。

**若继续做，优先级排序**：
1. 接入真实企业文档，扩评测集并做统计显著性检验；
2. 加入 Reranker 微调 / 领域词典，进一步压假拒答；
3. 引用校验升级为"逐句 entailment"（当前是逐字子串匹配）；
4. 多租户 + 权限过滤下推到向量层。

---

## 六、一句话总结

> 这个项目最花时间的不是"把链路搭起来"，而是**把"看起来对"的东西逐个证伪，改成"确实对"**。
> RAG 的难点从来不是"能不能答"，而是**"答得对不对、对不对得上、不该答时敢不敢不答"**。

# 知枢 · 架构设计详解

> 面向"想读懂代码"的读者。本文按**数据流**讲清每个模块的职责、接口与设计取舍。
> 全部约 3500 行 Python，每处关键决策都有"设计要点"注释（源码内）。

## 一、分层总览

```
┌─────────────────────────────────────────────────────────────────┐
│                         接入层 app/api                            │
│   /ask  /ask/stream(SSE)  /ingest  /stats  /docs/list  /health    │
└───────────────────────────────┬───────────────────────────────────┘
                                │
┌───────────────────────────────▼───────────────────────────────────┐
│                    门面 app/pipeline.ZhishuPipeline                │
│   ingest()  ask()  refresh_index()  stats()                       │
└───┬───────────────────────────────────────────────────────────────┘
    │
    ├── 入库链路 ──▶ app/ingest ──▶ app/storage
    │     parsers(解析) → chunker(分块) → llm.embed(向量化) → 落库
    │
    └── 问答链路 ──▶ app/retrieval ──▶ app/generation
          改写/HyDE → 混合召回 → RRF → 重排 → 父块回溯 → 生成 → 引用校验

        横切能力：app/core（配置 / LLM 客户端 / 可观测）  app/eval（评测）
        存储抽象：app/storage（向量库 / 元数据 / 缓存，均双后端 + 降级）
```

**依赖方向是单向的**：接入层 → 门面 → 各能力层 → 存储抽象。
`core` 只被依赖，不依赖业务；`storage` 不知道检索的存在。这样每一层都能独立测试。

## 二、核心模块逐个拆

### 2.1 `app/core/config.py` — 配置即开关

用 Pydantic Settings 统一管理所有可调参数，**每个降级开关都是一个环境变量**：

```python
vector_backend: str = "milvus"     # milvus | local
metadata_backend: str = "postgres" # postgres | sqlite
cache_backend: str = "redis"       # redis | memory
refuse_norm_threshold: float = 0.25  # 批内归一化拒答阈值
```

`llm_is_mock` 属性是个关键设计：**只要没配 Key，全链路自动进入 mock 模式**，
不抛异常、不中断，让"没 Key 的人也能跑通看懂"。

### 2.2 `app/core/llm_client.py` — 统一模型客户端

一个 `LLMClient` 封装三类调用：`chat` / `embed` / `rerank`，背后可以是百炼、DeepSeek、OpenAI 兼容接口，也可以是 mock。

**两个关键设计**：

1. **错误分类重试**：把异常分成两类——
   - `TransientError`（429 / 5xx / 超时）→ **指数退避 + 抖动**重试；
   - `DeterministicError`（400 参数错）→ **不重试**（重试也没用，只会浪费配额）。

   ```python
   def classify_http_error(status, body) -> type[Exception]:
       if status in (429, 500, 502, 503, 504): return TransientError
       return DeterministicError
   ```

2. **确定性 mock**：无 Key 时，`embed` 用 **md5 哈希生成确定性向量**（同一文本永远同一向量），
   `chat` 返回**结构化 JSON**（这样引用校验链路仍可被测试）。

### 2.3 `app/storage/` — 三个存储，三套降级

**`vector_store.py`**：`VectorStore` 抽象 + 两个实现。

- `MilvusVectorStore`：HNSW 索引（`M=16, efConstruction=200`），度量 `IP`。
  - **只对 child 建向量**——父块若也建向量，会和子块在同一空间竞争，且大块语义被稀释；
  - **delete 前必须 `load()`**：Milvus 的经典坑，否则报 "collection not loaded"；
  - **insert 后 `flush()`**：Milvus 写后可见是最终一致的，不 flush 检索不到。
  - **`drop()` 后立即重建并重新指向 collection**：否则旧句柄失效，再 insert 报 "collection not found"。

- `LocalVectorStore`：numpy 全量点积的暴力检索，`.npy` + `jsonl` 持久化。
  - 设计考虑：**数据量 < 10 万且 QPS 不高时，暴力检索完全够用且零运维**。"先量规模再选型"比"一上来就上分布式"更专业。

**`meta_store.py`**：`MetaStore` 双后端（PG / SQLite），三张表 `documents` / `chunks` / `qa_logs`。
- 关键方法 `get_parent_chunks`：**small-to-big 的"取父块"**接口，检索命中 child 后回带父块全文；
- 用 `?` 占位符 + `_ph` 属性做 **PG/SQLite 方言适配**（PG 用 `%s`）。

**`cache.py`**：`RedisCache` / `MemoryCache`。

- 缓存键 = `zhishu:{版本号}:{namespace}:{内容hash}`；
- **版本号入键是防脏读的关键**；
- **版本号存 Redis（不是进程内存）**——多进程/重启都不失效（详见制作过程难点 5）。

### 2.4 `app/ingest/` — 解析与分块

**`parsers.py`**：三级降级解析。

```
parse_document(path)
  ├─ .md/.txt/.csv ──▶ TextParser（按后缀直接分发，关键！）
  └─ .pdf ──▶ 文本层探测链
        ├─ 有文本层且非扫描 → PyMuPDFParser（含两栏检测）
        ├─ MinerU 可用 → MinerUParser（版面/表格/公式）
        └─ 扫描件 → PaddleOCRParser
```

统一产出 `ParsedDoc(blocks=[ParsedBlock(text, page, bbox, type)])`。

**`chunker.py`**：语义分块 + 父子块构建。

- `semantic_chunk_blocks`：按句子边界聚合到目标 token 数，带**重叠窗口**（`CHUNK_OVERLAP=64`）；
- `build_parent_child`：若干相邻 child 归一个 parent；
- **`chunk_document` 的赋值顺序**：先定父块 id → 再回填 child.parent_id（见制作过程难点 4）。

### 2.5 `app/retrieval/hybrid_retriever.py` — 混合检索

**四步**：

1. **查询改写** `rewrite_query`：把口语化问题扩成检索友好的关键词（如"年休假"→"年休假 带薪年假 顺延期限 有效期 截止时间 过期作废"）；
2. **HyDE**：让模型先"假设一个答案"，用假设答案去检索（对抽象问题有效）；
3. **双路召回**：向量 top-K + BM25 top-K（`jieba` 分词，**保留字母数字**以匹配编号/型号）；
4. **RRF 融合**：

   ```python
   def reciprocal_rank_fusion(rankings, k=60):
       # score = Σ 1/(k + rank_i)，只用排名不用分数 → 天然跨量纲
   ```

**过滤条件下推**：`_build_expr` 把 `{dept: "人力资源", doc_type: "policy"}` 拼成 Milvus `expr`，
在**向量库内过滤**而不是检索完再筛，既快又准。

### 2.6 `app/generation/rerank_generate.py` — 重排 + 生成治理（项目最核心）

**重排** `Reranker.rerank`：调 Cross-Encoder 对 (query, doc) 精排，失败则**降级回 RRF 顺序**（不能让重排挂掉整条链路）。

**父块回溯** `expand_parent`：small-to-big 的"big"。
- **去重**：多个 child 命中同一 parent，父块只保留一次；
- **关键修复**：child 的 `text` **保留原文**（可精确引用），父块放 `parent_text`（做语境）。

**生成治理三道防线**：

```
① 结构化输出：强制 JSON（answer/citations/confidence/refused/reason）
② 引用校验  ：validate_citations —— 逐字比对，丢幻觉编号，编号自愈
③ 证据不足拒答：批内归一化 + 相对阈值（防假拒答）
```

**引用校验的细节**：

| 机制 | 作用 |
|---|---|
| `evidence_id ∉ id_map` → 丢弃 | 防幻觉引用（引用了不存在的证据） |
| `quote` 逐字子串匹配 → `verified` | 把"引用"变成可机器验证的事实 |
| **编号自愈** `corrected` | quote 在别的证据里能找到 → 自动改正编号 |
| **正文回填** `_backfill_citations` | 模型只写正文不填数组 → 正则提取补全 |
| **空 quote 兜底** `_backfill_quote` | quote 为空 → 用证据原文兜底（标记 `quote_source=system`） |

**拒答判定**：

```python
top_norm, top_score = _normalized_top(scores)   # 批内 min-max 归一化
low_evidence = (not candidates) or (top_norm < 阈值 and top_score <= 0)
```

### 2.7 `app/core/observability.py` — 可观测

**Span / TraceRecorder**：树形结构，每个 span 有 `trace_id` / `parent_id` / `kind` / `latency_ms` / `tokens` / `cost`。

**两个必须用"区间运算"的口径**：

```python
# 端到端墙钟 = 最晚结束 - 最早开始（不是 max(单个 span)）
total_latency_ms = (max(ends) - min(starts)) * 1000

# 阶段耗时 = 该阶段所有 span 的【时间区间并集】（重叠只算一次）
stage_breakdown() → 每个 kind 取 _union_len_ms(intervals)
```

**为什么不能简单求和/取最大**：span 之间有**嵌套**（retrieve 下有 query_rewrite/vector_recall/hyde），
求和会重复计入，取最大会漏掉串行段。只有区间并集才是真实墙钟。这个坑在制作过程难点 8 有详述。

**计费**：`PRICE_TABLE` 按模型 + token 数算成本，mock 恒为 0。

### 2.8 `app/eval/harness.py` — 评测与门禁

四个指标：`faithfulness` / `answer_relevancy` / `context_recall` / `llm_judge`。

**门禁的关键设计**：按**单项下限**卡，不是平均值。

```python
def check_gate(summary):
    # 拒答准确率必须 100%！这是企业场景的底线
    if refuse["correct"] != refuse["expected"]:
        failures.append("拒答准确率未达 100%")
    for metric, floor in METRIC_FLOORS.items():
        if summary["metrics"][metric] < floor:
            failures.append(f"{metric} 低于下限")
```

为什么不是平均值？——**平均分会掩盖致命短板**。faithfulness 0.99 + 拒答率 50%，平均看着不错，
但"一半该拒答的没拒答"意味着系统在编造，企业不可接受。

### 2.9 `app/pipeline.py` — 门面

把上面所有能力编排成两个方法：`ingest(path)` 和 `ask(query)`。
**设计考虑**：为什么要有门面层？——让 API 层和脚本层用**同一套编排**，避免"接口一套逻辑、脚本另一套"。

### 2.10 `app/api/routes.py` — 接口

`/ask`（普通）、`/ask/stream`（SSE 流式）、`/ingest`、`/stats`、`/docs/list`、`/health`。
流式用 SSE 逐 token 推送，前端实时渲染。

## 三、一次问答的完整时序

```
用户: "采购5万元设备谁审批？"
  │
  ├─ ① 缓存查询（键含 KB 版本）──命中─▶ 直接返回
  │
  ├─ ② [span] retrieve
  │     ├─ 查询改写：→ "采购 设备 5万元 审批权限 审批流程 审批人"
  │     ├─ [span] vector_recall：Milvus 向量 top-20
  │     ├─ [span] bm25_recall  ：BM25 top-20（命中"审批"等词）
  │     └─ [span] rrf_fusion   ：融合 → top-10
  │
  ├─ ③ [span] rerank：百炼 gte-rerank 精排 → top-4
  │     └─ expand_parent：命中 child → 回溯父块（child 原文保留 + parent_text 附上）
  │
  ├─ ④ [span] generate：拼证据区 [证据1..N] → 强制 JSON 输出
  │     └─ 答案："须经总经理审批 [证据1]"
  │
  ├─ ⑤ 引用校验：quote 逐字比对证据1原文 → verified=true
  │
  ├─ ⑥ 拒答判定：批内归一化 top 分 > 阈值 → 不拒答
  │
  └─ ⑦ 写 trace + metrics + qa_log，回填缓存
```

## 四、测试策略

34 个测试，分 8 类，**全部走降级后端**（CI 无需外部服务）：

| 测试类 | 锁定的关键行为 |
|---|---|
| `TestParsers` | 按后缀分发（`.md` 不走 PDF 解析器） |
| `TestChunker` | 父子块关系、重叠窗口、父 id 先定稿 |
| `TestObservability` | 墙钟 = 区间并集；**阶段耗时也是并集**；计费只来自真实模型 |
| `TestRRF` | RRF 奖励多路共识 |
| `TestFilterExpr` | 过滤条件下推表达式生成 |
| `TestGenerationGovernance` | 丢幻觉引用、`verified` 标记、**归一化拒答**、**空 quote 兜底**、**缓存有上限**、父块去重 |
| `TestStorageFallback` | 缓存键含版本号 |
| `TestEndToEnd` | 入库→问答全链路；幂等入库；空库拒答 |

**每个回归测试都对应一个真实修复**（见 `tests/test_core.py` 的注释），防止问题回退。

# 知枢 · 面试问答手册

> 用法：面试前通读一遍，重点记**"我做了什么、为什么这么做、踩了什么坑、怎么解的"**。
> 每题都标了考察点。带 ⚠️ 的是**高频追问**，务必准备。
> 原则：**如实讲你真正做过的**；没做过的部分坦白说"这块是下一步规划"。

---

## 一、开场：一句话讲清这个项目

> "知枢是一个企业级 RAG 知识中枢，把公司散落在 PDF/Word/扫描件里的制度文档，
> 变成一个**能自然语言提问、答得可溯源、答不了就拒答**的问答系统。
> 技术上完整实现了**解析→分块→向量化→混合检索→重排→生成治理→引用溯源**全链路，
> 大约 3500 行 Python，34 个单测，从 0 到 1 自己搭的。"

**如果面试官只给你 30 秒**：抓住三个关键词——**可溯源、会拒答、能降级**。

## 二、架构与链路（必问）

### Q1. 讲一下你的 RAG 完整链路。

**考察点**：是否真的懂 RAG，而不是"调了个 API"。

**答**：
> 分入库和问答两条链路。
> **入库**：文档解析（三级降级）→ 语义分块（带重叠）→ 父子块构建 → 向量化 → 落库（Milvus 存向量、PG 存元数据）。
> **问答**：查询改写 + HyDE → 向量和 BM25 双路召回 → RRF 融合 → Cross-Encoder 重排 → 父块回溯 → 强制 JSON 生成 → 引用校验。
> 两条链路都用 Span 树做可观测，能下钻看每一段的耗时。

### Q2. ⚠️ 为什么要做"混合检索"？只用向量不行吗？

**考察点**：是否理解向量检索的短板。

**答**：
> 不行。向量擅长**语义匹配**（"顺延到什么时间"能匹配到"跨年使用期限"），但对**精确串很弱**——
> 比如"第三条""GB/T 1234""SN-2024-001"这种条款号、型号、编号，向量经常召回不准。
> 企业文档里恰恰大量存在这类精确匹配需求，所以必须再加一路 **BM25** 关键词召回。
> 两路各有所长，缺一不可。

### Q3. ⚠️ 两路召回的分数量纲不一样，怎么融合？

**考察点**：RRF 的理解深度。**这是高频追问**。

**答**：
> 我用的是 **RRF（Reciprocal Rank Fusion）**，公式 `score = Σ 1/(k + rank_i)`，k 取 60。
> 关键点是：**RRF 只看排名、不看分数**。向量分是余弦 0~1，BM25 是 0~十几，量纲完全不同，
> 如果加权求和，就得先归一化，而归一化方式很敏感、换个模型就要重调。
> RRF 只用排名，天然跨量纲，**零调参**。

### Q4. 为什么要重排？向量召回不够吗？

**考察点**：bi-encoder vs cross-encoder。

**答**：
> 一句话：**召回求全，重排求准**。
> 向量检索是**双塔模型**，query 和 doc 分开编码，快但粗，适合从海量文档里"粗筛"；
> 重排是 **Cross-Encoder**，把 query 和 doc 拼在一起过模型，能捕捉细粒度交互，准但慢。
> 所以我先用便宜的向量召回拿 top-20，再用贵的重排精挑 top-6。
> 如果直接拿向量 top-1 喂给 LLM，精度会差一截。

## 三、核心设计：父子块（small-to-big）

### Q5. ⚠️ 什么是父子块？为什么不直接切固定长度？

**考察点**：**本项目最核心的设计**，必问。

**答**：
> 固定长度切块有个两难：**切太小丢上下文（断章取义），切太大召回不准（语义被稀释）**。
> 父子块把这两件事拆开：**child 小块负责"找到"，parent 大块负责"看懂"**。
> 检索用 child（向量聚焦、召回准），命中后回溯它的 parent（上下文完整）喂给 LLM。
> 一句话——**小块做证据、大块做语境**。

### Q6. ⚠️ 父块要不要也建向量？

**考察点**：是否理解"检索单元"和"生成上下文"的区别。

**答**：
> **不建。只对 child 建向量。**
> 因为父块是"生成上下文"，不是"检索单元"。如果父块也建向量，它会和子块在同一空间竞争，
> 而且大块向量语义被稀释，反而**拉低召回精度**。
> 正确用法是：**只检索子块 → 命中后回溯父块喂 LLM**。

### Q7. ⚠️ 父块回溯的时候要注意什么？（这题藏着我的一个真实 bug）

**考察点**：细节掌握程度，能不能讲出"踩过的坑"。

**答**：
> 三个细节：
> 1. **去重**：多个 child 命中同一 parent，父块只能出现一次，否则同一份长文本重复塞进 prompt，浪费 token 还挤掉其他证据；
> 2. **父块缺失要兜底**：元数据没同步时退回 child 原文，不能让链路断掉；
> 3. **⚠️ 最关键的一点——child 原文必须保留，不能被父块覆盖**。
> 这是我踩的坑：早期我把 child 的 text 直接**替换成父块全文**，结果引用指向的"块"变成了放大后的父块，
> 用户点开对不上；而且模型看到的是融合文本，容易按"第几条证据"数位置**乱标编号**。
> 后来改成：**child 保留自己的原文（用于逐字引用、高亮命中），父块放到独立的 `parent_text` 字段做语境**。
> 改完之后引用从"✗未核对"变成全部"✓已核对原文"。

## 四、生成治理与引用（项目亮点）

### Q8. ⚠️ 你怎么保证模型不乱标引用？（防幻觉引用）

**考察点**：**项目最亮点，必问**。

**答**：
> 我把"引用"从**模型的礼貌承诺**变成**可机器验证的事实**，做了几层：
> 1. **强制 JSON 输出**，引用结构化成 `{evidence_id, quote}`；
> 2. **编号校验**：`evidence_id` 不在真实证据范围内 → 判定幻觉，**直接丢弃**；
> 3. **逐字比对**：`quote` 必须在对应证据原文里**逐字子串匹配**才能算 `verified=true`，我做了归一化（去空白、转小写）；
> 4. **编号自愈**：如果 quote 在当前证据里找不到，但在**另一条证据**里能找到，说明模型只是编号填错了、内容是对的 → **自动纠正编号**并标记 `corrected=true`。
>
> 每一步都有回归测试。

### Q9. ⚠️ 如果模型把编号写在正文里，但 citations 数组是空的呢？

**考察点**：是否遇到过真实的边角问题。

**答**：
> 遇到过，很典型。模型习惯把 `[证据N]` 写在 answer 正文里，但 `citations` 数组留空。
> 这会导致一个**隐蔽的假阳性**：引用校验对空数组是"0/0 通过"，看着没问题，
> 但实际上"句级引用溯源"完全失效了——用户看到编号却点不开任何证据。
> 我的解法是**从 answer 正文正则提取 `[证据N]` 回填 citations**，保证"正文标注"和"结构化引用"始终一致。

### Q10. 你的 `verified=false` 出现过假阴性吗？

**考察点**：能不能讲清一个具体的调试过程。

**答**：
> 出现过。模型明明引用了正确的句子，却判"未核对原文"。
> 排查发现是**证据原文在两个地方分别登记**（生成时一处、校验时一处），
> 两处的遍历顺序和范围一旦不一致，"校验用的原文"就和"喂给模型的原文"对不上。
> 修复原则是：**产生证据编号的地方，就必须是登记证据原文的地方**——单一事实来源。
> 我把登记动作内聚进了 `build_evidence_block`，消除两处不一致的可能。

### Q11. ⚠️ 你怎么做到"证据不足就拒答"？阈值怎么定？

**考察点**：**这是我踩的最重要的一个坑**，高分题。

**答**：
> 先说踩的坑：我最开始用 **rerank 原始分 < 固定阈值 0.35** 判拒答。
> 结果**假拒答**频发——问我"5 万设备谁审批"，语料里明明有，系统却拒答了。
> 追进去看，正确的块在融合阶段排第 1，但重排后 top 分只有 **0.19**，低于 0.35 就被判"证据不足"。
> 根因是**拿绝对分比固定阈值**：不同 reranker 分数量纲完全不同，百炼 gte-rerank 对真正相关的块也只给 0.19。
>
> 修复方案：改成**批内归一化 + 相对阈值**。同一个 query 的候选自成可比集合，
> `(score - min)/(max - min)` 归一化后量纲无关；只有"整批归一化后 top 分仍很低"**且**"绝对分≈0"才拒答。
> 好处是**换 reranker 不用重调阈值**。
> 修复效果很直观：** faithfulness 从 0.8 提升到 1.0**——假拒答直接把正确答案吞了。

### Q12. 拒答为什么重要？多选题里为什么拒答要 100% 准确？

**考察点**：企业价值观。

**答**：
> 企业场景里，**"答错"比"不答"危害大得多**。员工问"报销要多久"，系统编一个"7 天"，
> 员工照着做，可能被财务打回、甚至违规。所以我的底线是：**宁可拒答，不可编造**。
> 门禁里我把**拒答准确率设为 100%**，而且门禁是**按单项下限卡、不是平均值**——
> 因为平均分会掩盖致命短板：faithfulness 0.99 + 拒答率 50%，平均看着不错，
> 但"一半该拒答的没拒答"意味着系统在编造，企业完全不可接受。

## 五、工程化与可观测

### Q13. ⚠️ 怎么统计端到端延迟？为什么不是 max(某个 span)？

**考察点**：**经典陷阱题**，我在两个项目里都踩过。

**答**：
> 必须是**时间区间的并集**：`最晚结束 - 最早开始`。
> 因为 RAG 的各阶段是顺序执行的，最长的那一段绝不等于端到端。
> 比如 retrieve 3.8s + rerank 0.2s + generate 5.1s，端到端是 ~9.2s；
> 如果取 max 就只有 5.1s，**低估了快一半**。
>
> 而且这个坑我还有**升级版**：`stage_breakdown`（按阶段拆分耗时）我一开始是**把同 kind 的 span 求和**。
> 结果出现了 retrieve 阶段 10690ms、端到端只有 5950ms 的**物理上不可能**的结果。
> 根因是 retrieve 阶段内部**嵌套**了 query_rewrite / vector_recall / hyde 等子 span，
> 求和把子 span 重复计入了。**正确做法同样是取该阶段所有 span 的时间区间并集**。
> 所以我的结论是：**时间统计必须用区间运算，不能用简单加减**。

### Q14. 模型调用失败了怎么办？

**考察点**：健壮性设计。

**答**：
> 两个层面：
> 1. **错误分类重试**：把异常分成 `TransientError`（429/5xx/超时，可重试）和 `DeterministicError`（400 参数错，重试没用）。
>    前者走**指数退避 + 抖动**重试，后者直接失败，避免浪费配额。
> 2. **降级不中断**：重排失败就退回 RRF 顺序继续生成，不能让一个环节挂掉整条链路；
>    生成失败就返回拒答，绝不让用户看到堆栈。

### Q15. 缓存怎么设计？知识库更新了旧缓存怎么办？

**考察点**：缓存一致性的经典问题。

**答**：
> 缓存键 = `命名空间 + 知识库版本号 + 内容hash`，**版本号入键是防脏读的关键**。
> 每次重建索引就 `bump_kb_version()`，版本号 +1，所有旧缓存立即失效。
> 这里我踩过**两个坑**：
> ① 早期用 `int(time.time())` 当版本号——同一秒内批量入库两个文档会拿到**相同**版本号，缓存不失效；改成**单调递增计数器**。
> ② 后来发现计数器放在**进程内全局变量**里——多进程部署时各进程各一份，进程重启后归零，**历史旧缓存会重新可见**。
>    我在本地真实复现了"重启后又看到旧答案"。最终改成**版本号存 Redis**（共享、持久），进程内只做后备。

### Q16. 你的系统没有 Milvus / PG / Redis 能跑吗？

**考察点**：工程意识、开源友好度。

**答**：
> 能，**全链路每一个外部依赖都有降级**：
> Milvus 没有 → numpy 暴力检索；PG 没有 → SQLite；Redis 没有 → 进程内 LRU；模型 Key 没有 → 确定性 mock。
> 这不是妥协，而是设计目标之一——**让读者零门槛复现**。
> CI 里就跑的降级模式，34 个测试不需要任何外部服务。

## 六、评测

### Q17. ⚠️ 你怎么衡量这个 RAG 系统好不好？

**考察点**：有没有量化意识。

**答**：
> 我做了 4 个指标：**Faithfulness**（答案是否有证据支撑）、**Answer Relevancy**（是否切题）、
> **Context Recall**（检索是否召回了该召回的）、**LLM-as-Judge**（模型打分）。
> 另外单列**拒答准确率**。
> 评测集 10 题，含 **2 个库外负例**（专门测拒答）。
> 我把它做成了 **CI 门禁**——按**单项下限**卡，不达标就退出码非 0，拒绝合并。

**真实结果**（可复现）：
| 指标 | 数值 |
|---|---|
| faithfulness / relevancy / context_recall | 1.0 / 1.0 / 1.0 |
| llm_judge | 0.7 |
| 拒答准确率 | 2/2 |
| 平均延迟 / P95 | 6.9s / 9.1s |
| 单次成本 | ≈ $0.0009 |

**追问：为什么门禁用单项下限而不是平均分？**
> 因为平均分会掩盖致命短板——见 Q12。

### Q18. 你的评测集只有 10 题，指标可信吗？

**考察点**：诚实度 + 批判性思维。**这题一定要诚实**。

**答**：
> **坦白说，10 题的评测集是"功能验证"，不是统计意义上的基准**。
> 它的作用是保证"链路是对的、改动没把功能弄坏"（类似冒烟测试 + 回归）。
> 指标数值只能说明"在这套小语料上链路是正确的"，**不代表泛化能力**。
> 我在 README 里也明确写了这个局限。
> 如果要上生产，下一步是**接入真实企业文档、扩到几百题、做统计显著性检验**。

## 七、压力与反问

### Q19. 这个项目最大的难点是什么？

**答**：
> 最花时间的**不是把链路搭起来，而是把"看起来对"的东西逐个证伪、改成"确实对"**。
> 我踩了十几个**不报错但结果变差**的坑：children 没 append、父块 id 指向失效、缓存版本号不生效、
> 假拒答、引用张冠李戴……每一个都是"不崩溃、只是悄悄让系统变笨"。
> 所以我的原则是"**跑通不算数，要跑对**"，每修一处都补一个回归测试。

### Q20. 如果让你继续优化，你会做什么？

**答**（按优先级）：
> 1. 接入真实企业文档，把评测集扩到几百题，做统计显著性；
> 2. 引用校验从"逐字子串匹配"升级为"逐句 entailment"，能识别同义改写；
> 3. 多租户 + 权限过滤下推到向量层（现在过滤条件已能下推到 Milvus expr，但没做租户隔离）；
> 4. 引入领域词典 / 微调 reranker，进一步压假拒答。

### Q21. 这个项目有什么不足？

**考察点**：能不能客观评价自己的东西。

**答**：
> 1. 语料和评测集都太小，是功能验证不是基准；
> 2. 没做鉴权、多租户、限流，聚焦在 RAG 链路本身；
> 3. 引用校验是逐字匹配，对"同义改写"的引用会误判；
> 4. 生成阶段比较依赖模型遵循 JSON 指令，换较弱的模型可能要加 function calling 或 grammar 约束。

## 八、可能的动手题

### Q22. 给你一篇新文档，怎么入库？

```bash
python -m scripts.ingest path/to/doc.pdf --dept 人力资源
```
或在代码里 `pipeline.ingest(path, dept="人力资源")`。入库是**幂等**的（doc_id 基于路径）。

### Q23. 现场改一个参数，比如让拒答更保守？

改 `.env` 的 `REFUSE_NORM_THRESHOLD`（归一化阈值，调大更保守）或 `REFUSE_FLOOR`，重启即可，无需改代码。

### Q24. 如果要支持"多轮对话"（追问），你怎么改？

**答**：
> 现在的 `ask` 是单轮的。要支持追问，核心是**查询改写时把历史对话带上**——
> 把"那它的上限呢"这类依赖上下文的问题，改写成"XX 规定的上限是多少"这种自包含查询，再进检索。
> 我的检索链路已经有 `rewrite_query` 这个扩展点，只要给它加上对话历史就行。
> 另外缓存键要加会话维度，避免不同会话串答案。
